# Задача для фронтенда: интерфейс ведомостей

## Цель

Сделать первый рабочий интерфейс преподавателя для контрольной ведомости и ведомости посещаемости лекций. Интерфейс должен обращаться к существующему API, показывать пользователю результат операций и не содержать демонстрационных данных, которые выглядят как реальные.

## Перед началом

Изучи следующие файлы:

- `docs/project.md`
- `docs/glossary.md`
- `docs/business-rules.md`
- `docs/use-cases.md`
- `docs/api.md`
- существующие шаблоны в `src/main/resources/templates`
- существующие стили в `src/main/resources/static/css`

Работай в отдельной ветке. Не меняй доменную модель, JPA-модели, миграции и логику агрегатов. Если обнаружишь, что для интерфейса всё ещё не хватает backend API, опиши конкретный недостающий контракт, не создавая фиктивные данные или неподтверждённые маршруты. Не добавляй комментарии в код.

## Текущая граница API

API находится под префиксом `/api`, использует серверную сессию и сам определяет пользователя и его роль. ID преподавателя или деканата в теле запроса передавать нельзя. Подробности и примеры ответов находятся в `docs/api.md`.

Существуют следующие операции записи:

### Контрольная ведомость

- `PUT /api/control-sheets/{sheetId}/results/{studentId}/numeric`
- `PUT /api/control-sheets/{sheetId}/results/{studentId}/pass-fail`
- `POST /api/control-sheets/{sheetId}/close`
- `POST /api/control-sheets/{sheetId}/reopen`
- `POST /api/control-sheets/{sheetId}/archive`

Числовой результат отправляется с телом `{"score":88,"reason":"Пересдача"}`. Причина необязательна. Для зачёта/незачёта используется `{"result":"PASS","reason":"Пересдача"}`, допустимые значения `result`: `PASS` и `FAIL`. Причина при переоткрытии или архивировании также необязательна. Закрытие выполняет преподаватель; переоткрытие и архивирование доступны деканату.

### Ведомость посещаемости

- `POST /api/attendance-sheets/{sheetId}/lectures`
- `PUT /api/attendance-sheets/{sheetId}/lectures/{lectureId}/attendance/{studentId}`
- `POST /api/attendance-sheets/{sheetId}/close`
- `POST /api/attendance-sheets/{sheetId}/archive`

Лекция создаётся телом `{"date":"2026-10-05","title":"Введение"}`. Отметка посещения отправляется телом `{"status":"PRESENT"}` или `{"status":"ABSENT"}`. Закрытие выполняет преподаватель; архивирование доступно деканату.

Успешные команды, кроме создания лекции, возвращают `204 No Content`. Создание лекции возвращает `201 Created` и объект с `id`, `date`, `title`.

## Чтение данных и аутентификация

Read API уже предоставляет необходимые данные:

- `GET /api/courses` — курсы, доступные текущему преподавателю, либо все курсы для деканата; ответ содержит ID и статусы ведомостей, а также признаки доступа к каждой части курса;
- `GET /api/control-sheets/{sheetId}` — сведения о контрольной ведомости, шкала оценок, студенты и внесённые результаты;
- `GET /api/attendance-sheets/{sheetId}` — сведения о ведомости посещаемости, список студентов, лекции и отметки. `status: null` означает, что отметка ещё не поставлена.

Схемы ответов и примеры находятся в `docs/api.md`. Не подменяй ответы моками и не захардкоживай реальные курсы, студентов или результаты. Не придумывай дополнительные маршруты.

Для всех браузерных запросов к `/api` используй общий клиент `window.CsasApi.request(path, options)` из `/api-client.js`. Для тела запроса передавай объект в свойстве `json`, например `{method: 'POST', json: {title: 'Введение'}}`. Клиент сам получает CSRF-токен перед входом и изменяющими запросами, обновляет его после входа, добавляет нужный заголовок и отправляет cookie сессии (`credentials: "same-origin"`). Не получай токен отдельно в компонентах страниц и не сохраняй пароль или токен в `localStorage` либо постоянном клиентском хранилище. Для входа используй `POST /api/auth/login`, для получения пользователя `GET /api/auth/me`, для выхода `POST /api/auth/logout`.

## Требования к интерфейсу

- Все пользовательские тексты на русском языке.
- Используй минималистичное оформление в стиле страницы входа: простая компоновка, светлый фон, сдержанные цвета и понятные формы. Не добавляй новый UI-фреймворк без необходимости.
- Не используй emoji, декоративные точки-разделители и длинное тире.
- Страница 404 должна содержать только обычный текст и ссылку для возврата. Не добавляй к ней отдельные стили и декоративные элементы.
- Страницы должны корректно отображаться на обычном экране ноутбука и на узком экране.
- Раздели формы для числового результата и зачёта/незачёта, чтобы нельзя было случайно отправить значение не того типа.
- Для действий закрытия, переоткрытия и архивирования показывай подтверждение с названием действия.
- Пока запрос выполняется, блокируй повторное нажатие на соответствующую кнопку и показывай состояние загрузки.
- После успеха показывай понятное подтверждение. Не показывай успех до ответа сервера.
- При сетевой ошибке сохраняй введённые пользователем значения и позволяй повторить запрос.
- Не очищай всю страницу после успешной операции.
- Не показывай формы действий, недоступных текущей роли, если роль известна интерфейсу. Независимо от этого корректно обрабатывай `403`, поскольку окончательная проверка прав выполняется сервером.
- Не добавляй расчёт рейтинга или итоговой оценки на фронтенде: это ответственность backend.

## Общий API-клиент и ошибки

Сделай переиспользуемый слой запросов к `/api`:

- отправляй JSON с корректным `Content-Type` для запросов с телом;
- не пытайся читать JSON у ответа `204 No Content`;
- при ошибке разбирай формат `ApiErrorResponse`: `timestamp`, `status`, `error`, `message`, `path`;
- показывай пользователю понятное сообщение, а HTTP-статус оставляй доступным для диагностики;
- `400` показывай как ошибку введённых данных;
- `401` как отсутствие или истечение аутентификации;
- `403` как недостаток прав;
- `404` как отсутствие ведомости, лекции или студента;
- `409` как конфликт состояния ведомости или операции;
- `422` как недопустимый результат;
- для неизвестной ошибки показывай нейтральное сообщение и не теряй технические сведения в консоли разработчика.

Не сохраняй пароль в URL, `localStorage` или постоянном клиентском хранилище. Не ослабляй требования безопасности и не отключай CSRF/аутентификацию для удобства интерфейса. Если для подключения страниц требуется определить способ входа, зафиксируй это как отдельную зависимость, не реализуя самовольный альтернативный механизм.

## Проверки и готовность

Перед PR:

- проверь, что проект собирается;
- вручную проверь отображение страниц в браузере;
- проверь состояния загрузки, успешного ответа, сетевой ошибки и ответов `400`, `401`, `403`, `404`, `409`, `422`;
- проверь, что запросы используют только перечисленные реальные маршруты и не передают ID актёра;
- проверь `git diff`, удали временные данные и незаконченные демонстрационные элементы.

PR готов, когда содержит:

- реализованные шаблоны и стили экранов контрольной и посещаемой ведомостей в пределах доступных данных;
- переиспользуемый API-клиент и понятную обработку ошибок;
- отсутствие фальшивых курсов, студентов, лекций и результатов;
- перечень оставшихся backend-зависимостей, если они обнаружены;
- краткое описание выполненных ручных проверок и известных ограничений.
