# Как мы работаем с git

Договорённости простые и рассчитаны на троих. Смысл у них один: в `main` всегда
лежит то, что собирается и работает, а незаконченное живёт в отдельных ветках.

## Первая настройка

Подписывайтесь настоящим именем, иначе в истории будет непонятно, кто что делал,
а на защите это спросят.

```
git config user.name "Имя Фамилия"
git config user.email "почта@example.com"
```

Клонируем репозиторий и проверяем, что проект собирается, до того как что-то
менять:

```
git clone <адрес репозитория>
cd <папка репозитория>
./mvnw test
```

## Ветки

Основная ветка называется `main`. Напрямую в неё не коммитим, даже мелочи.

Под каждую задачу заводим ветку от свежего `main`:

```
git switch main
git pull
git switch -c feature/course-rating
```

Имя ветки состоит из типа и короткого описания латиницей: `feature/exam-sheet`,
`feature/student-crud`, `fix/rating-division`, `docs/test-plan`. Тип нужен, чтобы
в списке веток было видно, где новая функциональность, где починка, где
документы.

Ветка живёт недолго. Если задача тянется больше нескольких дней, скорее всего её
стоило разбить.

## Коммиты

Коммитим часто и небольшими порциями. Так проще и читать историю, и откатывать
что-то одно.

Сообщение пишем по-русски, первой строкой коротко и в настоящем времени, что
сделано:

```
Добавляет расчёт рейтинга по курсу
Запрещает выставлять балл выше максимума работы
Правит целочисленное деление в расчёте рейтинга
```

Если в одну строку смысл не помещается, после пустой строки идёт абзац с
объяснением, зачем это понадобилось. Что именно поменялось, видно из диффа, а
вот почему, не видно никогда.

Не коммитим закомментированный код, отладочные `System.out.println` и файлы,
которые попали в индекс случайно. Перед коммитом смотрим, что добавляем:

```
git status
git diff
```

## Что не попадает в репозиторий

Собранные классы (`target/`), настройки IDE (`.idea/`, `*.iml`), локальные
конфиги с паролями и всё, что генерируется при сборке. Для этого есть
`.gitignore`, и если что-то лишнее всё равно просится в коммит, надо дополнить
его, а не добавлять файл руками.

Пароль от базы в `application.yaml` не храним. Локальные настройки держим в
отдельном .env (.env.example будет , который лежит в `.gitignore`.

## Перед тем как отправить ветку

Прогоняем тесты. Если они красные, чиним, а не отправляем со словами «потом
поправлю»:

```
./mvnw test
git push -u origin feature/course-rating
```

## Слияние

Изменения попадают в `main` через pull request. Даже если правка на две строки,
второй человек тратит минуту и смотрит на неё. Это не про недоверие, а про то,
что вы трое работаете над разными частями и должны хотя бы примерно
представлять, что происходит у соседа. Плюс на защите будет что показать, кроме
кода.

В описании pull request пишем, что сделано и как это проверить.

Смотреть в чужом коде стоит на три вещи: понятно ли, что делает код, не сломает
ли он соседний модуль, и есть ли тест, если добавилась формула или запрет.
Спорить о расстановке скобок не надо.

После слияния ветку удаляем, чтобы список не зарастал.

## Как не собирать конфликты

Раз в день подтягиваем свежий `main` в свою ветку:

```
git switch main
git pull
git switch feature/course-rating
git merge main
```

Основная защита от конфликтов не техническая, а организационная: каждый работает
в своём пакете. Пересекаемся мы в основном на `pom.xml` и на общих шаблонах,
поэтому если добавляете зависимость или правите общий шаблон, скажите об этом в
чате.

Если конфликт всё-таки случился, не разрешайте его наугад. Разберитесь, чей код
вы затираете, и если непонятно, спросите автора. Затёртая чужая работа обходится
дороже получаса разговора.

## Если что-то сломалось

Пока изменения не отправлены, почти всё можно откатить. Вернуть один файл к
состоянию из последнего коммита:

```
git restore src/main/java/com/dev/csas/course/Course.java
```

Посмотреть, что вообще происходило:

```
git log --oneline --graph --all
```

Ветку, которую уже видели остальные, не переписываем принудительным пушем.
`git push --force` в общую ветку это самый быстрый способ потерять чужие
коммиты.

## Отметки этапов

Задание разбито на пять этапов. Когда этап сдан, ставим на `main` тег, чтобы
потом можно было показать состояние проекта на любой момент:

```
git tag -a stage-1 -m "Этап 1: анализ предметной области"
git push origin stage-1
```
