# Миграции базы данных

Схему базы описываем миграциями Flyway. Hibernate схему не создаёт и не меняет.

## Почему не `ddl-auto: update`

`update` работает, пока проект маленький, и молча перестаёт работать, когда
что-то нужно поменять. Он добавляет таблицы и колонки, но никогда не удаляет и
не изменяет существующие. После переименования поля в базе останутся оба,
и никто
этого не заметит.

Для нас важнее другое. Документ 2 задания, ER-диаграмма, нормализованная до
третьей нормальной формы. При `update` схема получается побочным продуктом
аннотаций: диаграмму пришлось бы рисовать с того, что сгенерировалось. На
вопрос «почему здесь такая связь» ответа нет. При миграциях схема
проектируем мы, а диаграмма её описывает.

Плюс миграции лежат в репозитории. Любой из нас поднимает базу с нуля одной
командой и получает ровно ту же схему, что у остальных.

Поэтому в `application.yaml`:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

`validate` не трогает базу, но при старте сверяет её с сущностями и падает, если
они разошлись. Это ровно то, что нужно. Если забыли написать миграцию, узнаём
сразу, а не через неделю.

## Зависимости

В `pom.xml` нужен и стартер, и модуль поддержки PostgreSQL. Начиная с десятой
версии Flyway драйверы конкретных СУБД вынесены отдельно, и без второй
зависимости
запуск падает с `Unsupported Database: PostgreSQL`. Версии проставляет
Spring Boot, указывать их не надо.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

## Где лежат файлы и как называются

Каталог `src/main/resources/db/migration`. Имя файла:

```
V<метка времени>__<что делает>.sql
```

Метка времени включает год, месяц, день, часы и минуты, записанные слитно.
Дальше два подчёркивания и короткое описание латиницей в нижнем регистре.

```
V202609081935__create_groups.sql
V202609081947__create_students.sql
V202609091012__add_curator_to_groups.sql
```

Тестовые данные для локальной разработки находятся в
`src/main/resources/db/dev/migration` и подключаются только профилем `dev`.
Это отдельные миграции Flyway, они используют ту же схему `public`, но не
попадают в обычный запуск приложения.

Почему метка времени, а не `V1`, `V2`, `V3`: мы работаем втроём в параллельных
ветках. Два человека, отведя ветки от одного `main`, гарантированно возьмут
один и тот же следующий номер, и после слияния приложение не поднимется ни у
кого с ошибкой `Found more than one migration with version 2`. Совпасть до
минуты практически невозможно, и согласовывать ничего не нужно.

## Имена таблиц и колонок

Таблицы во множественном числе, `snake_case`: `users`, `teachers`, `groups`,
`students`, `disciplines`, `semesters`, `courses`, `course_students`,
`course_works`, `course_scores`, `control_sheets`, `control_results`,
`control_sheet_events`, `attendance_sheets`, `lectures`, `lecture_attendance`,
`coursework_sheets`, `coursework_results`.

Колонки тоже `snake_case`: `group_id`, `max_score`, `teacher_id`, `course_type`,
`start_semester_id`, `end_semester_id`, `admission_date`.

Слова берём из [глоссария](glossary.md). Если понятия там нет, сначала
добавляем его туда, потом пишем миграцию. Это дешевле, чем потом выяснять, что
в базе `subjects`, в коде `Discipline`, а на экране «дисциплина».

Отдельно про группы: `group` является зарезервированным словом SQL. В единственном числе
его пришлось бы брать в кавычки в каждом запросе. Множественное число снимает
проблему само.

## Применённую миграцию не редактируем

Никогда. Flyway хранит контрольную сумму каждого применённого файла, и правка
слитого в `main` файла роняет старт приложения у всех, кроме автора. У него база
уже накатана и всё работает. Если ошиблись, пишем новую миграцию сверху.

Пока в базе нет данных, схему можно свободно переделывать: снёс базу, накатил
заново. Как только мы наполним её тестовыми данными для сдачи, правило
становится жёстким.

## Первый запуск

Если база уже создана Hibernate'ом через `ddl-auto: update`, Flyway на ней
работать откажется: таблицы есть, а истории миграций нет. Базу надо пересоздать,
чтобы схема родилась из миграций:

```
docker compose down -v
docker compose up -d
```

Флаг `-v` удаляет том вместе с данными. На этом этапе терять там нечего.
Параметр `baseline-on-migrate` эту ошибку тоже убирает, но он зафиксирует как
исходное состояние схему, сгенерированную Hibernate, то есть ровно то, от чего
мы уходим. Не используем.

## Когда чужая миграция приезжает «задним числом»

Ты влил свою миграцию и накатил её. Через два дня вливается ветка соседа, а его
миграция старше твоей по времени. Он отвёл ветку раньше. Flyway по умолчанию
такую не применит и свалит проверку: `Detected resolved migration not applied to
database`. Причём у автора ветки всё работает, а падает у остальных.

Лечится пересозданием базы. Это самый честный путь. Схема каждый раз
собирается из миграций с нуля, ровно так же, как у преподавателя при
проверке. Если пересоздавать неудобно, есть аварийный выход:

```yaml
spring:
  flyway:
    out-of-order: true
```

Он разрешает применить опоздавшую миграцию задним числом. Для разработки
допустимо, в общий `application.yaml` не кладём.

## Перед тем как отправить ветку

- приложение поднимается на пустой базе с нуля;
- `ddl-auto: validate`, и приложение не падает при старте;
- имена таблиц и колонок есть в глоссарии;
- ранее слитые миграции не тронуты.
