# Учёт успеваемости студентов

Учебный проект по дисциплине «Информационные технологии», лабораторная работа 1.
Веб-система централизованного учёта успеваемости для деканата: студенты, группы,
дисциплины, баллы, ведомости и отчёты.

## Что стоит понять про модель сразу

**Курс** это один вид преподавания дисциплины одной группе. У курса есть тип:
`LECTURE`, `SEMINAR` или `COURSEWORK`, один назначенный преподаватель и семестр
начала и окончания. Эти семестры могут совпадать или различаться. Для одной
дисциплины у группы могут быть все три курса; их может вести как один, так и
разные преподаватели. Семинарный курс хранит работы и рейтинг. Лекционный курс
хранит лекции и посещаемость. Курсовой курс связан с отдельной ведомостью.

**Зачётная ведомость** это документ, в который преподаватель семинарного курса
вносит результат итогового контроля по каждому студенту: зачёт/незачёт,
результат экзамена или
дифференцированного зачёта. Её закрывают, а под пересдачу деканат открывает
заново. **Итоговая ведомость** строится на основании рейтинга курса и закрытой
зачётной ведомости: для экзамена и диф. зачёта результат переводится в оценку
от 2 до 5, для обычного зачёта переносится зачёт/незачёт.

**Ведомость курсовых работ** хранит отдельный балл от 0 до 100 для каждого
студента. Балл переводится в оценку по фиксированной шкале. Ведомость можно
переоткрыть в следующем семестре для пересдачи.

**Рейтинг** это величина от 0 до 100, доля набранных баллов от максимально
возможных. Не место в списке.

И главный принцип: храним то, что кто-то решил, вычисляем то, что из этого
следует. Баллы за работы, результаты контроля, курсовых работ и посещаемость
поставили преподаватели, значит они лежат в базе. Рейтинг и итоговые оценки
вычисляются из этих данных. Система не считает средний балл студента по всем
дисциплинам. Деканат самостоятельно решает, какие последствия имеют пропуски
лекций; система показывает посещаемость, но не назначает взыскания.

## Технологии

Java 21, Spring Boot, Thymeleaf, PostgreSQL, Maven. Тесты на JUnit 5 и AssertJ.

## Как запустить

Тесты предметной области базу не трогают, для них ничего поднимать не нужно:

```
./mvnw test
```

Для самого приложения нужна база. Достаточно:

```
cp .env.example .env
./mvnw spring-boot:run
```

Чтобы запустить приложение с демонстрационными данными, используй профиль `dev`:

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
```

Он добавляет демоданные в схему `public`. Подробности о профиле, тестовых
учётках и запуске из IntelliJ IDEA описаны в [docs/development.md](docs/development.md).

Spring Boot через зависимость `spring-boot-docker-compose` сам поднимает
сервисы из `compose.yaml` (PostgreSQL и pgAdmin). Отдельно вызывать
`docker compose up -d` не нужно: если контейнеры уже запущены вручную, возможен
конфликт порта `5432`.

Вместе с PostgreSQL поднимается pgAdmin, он открывается на
http://localhost:5050 с почтой и паролем из `.env`. Внутри него адрес сервера
не `localhost`, а `postgres`, потому что контейнеры видят друг друга по именам
сервисов, а порт 5432. С хоста же база доступна как обычно на `localhost:5432`.

Остановить всё: `docker compose down`. Если нужно снести и данные, добавьте
`-v`, но помните, что это удалит содержимое базы без вопросов.

## Структура репозитория

```
docs/     проектная документация
src/      исходный код и тесты
pom.xml   сборка и зависимости
```

Внутри `src/main/java` код разложен по предметным областям, а не по слоям. То есть пакет
`course` содержит и модель курса, и его контроллеры, и работу с базой, а не
лежит размазанным между `model`, `controller` и `repository`. Так проще держать
границы между модулями и понимать, кого затронет ваша правка.

Их три, всё остальное на усмотрение автора модуля.

Новое понятие сначала попадает в глоссарий, потом в код.

Каждый работает в своём пакете, чужие без предупреждения не трогаем.

Если написали формулу или запрет, рядом кладите тест. Контроллеры, шаблоны и
геттеры покрывать не нужно.
